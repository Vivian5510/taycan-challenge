## 1、业务背景
Taycan 是快手自研的高性能持久化 KV 存储引擎（Taycan的实现设计），广泛应用于推荐、广告等核心业务链路。Taycan 采用纯内存哈希索引，所有 key 的索引信息常驻内存，读写性能高、延迟极低。
(Taycan 内存索引+磁盘存储架构图)*
然而随着业务规模持续增长，当 key 数量达到数亿乃至数十亿量级时，纯内存索引方案面临严峻的 OOM（Out of Memory）风险，这是 Taycan 当前面临的核心瓶颈之一。Taycan 目前已经完成磁盘索引置换的开发和测试，在内存不足时可将部分桶的索引换出到磁盘。为进一步降低重启恢复开销和索引加载延迟，本命题希望设计一个可持久化的磁盘索引结构，支持磁盘索引按需加载到内存，并在索引内存占用超过阈值后自动落盘、释放内存。
> [原文对象占位符；对象详情保留在原始快照中]
**【核心概念说明】**
索引持久化（Index Persistence）：将 key 到数据位置的索引信息组织为可持久保存、可按需访问的磁盘索引结构。访问时，仅将所需的索引加载到内存；当索引内存占用超过阈值时，自动将部分内存索引落盘，确保相关索引更新可恢复后释放内存。引擎重启后能够恢复并使用磁盘索引，无需将全部索引加载到内存。整个过程对上层调用完全透明。
Compaction：随着写入和删除操作不断积累，磁盘上会存在大量过期/被覆盖/被删除的无效数据。Compaction 负责后台扫描并回收这些无效数据，避免磁盘空间持续膨胀。
Checkpoint：参考 RocksDB 的 Checkpoint，为引擎某一时刻的状态生成一份可在独立目录中重新打开的一致性副本，包含数据、索引及恢复所需的元数据和日志。副本创建完成后，原引擎后续的写入、删除和 Compaction 不影响该副本，可用于备份、迁移和恢复。实现时可复制文件，也可对同一文件系统内不再修改的文件使用硬链接，减少复制开销；仍会修改的文件需要单独处理，保证副本内容不变。本命题将该能力作为可选加分项。

## 2、问题详情
现有索引置换方案缓解了索引常驻内存带来的容量压力，但索引从纯内存访问转向内存与磁盘协同后，仍面临以下问题与挑战：
加载粒度的权衡：一次查询可能只需要一个 key 的索引，但加载整个桶会引入大量无关索引，占用内存并可能触发其他索引换出。加载粒度过小，又可能增加随机 I/O 和索引管理开销。在访问范围较广、热点变化的情况下，频繁加载和换出会进一步放大长尾延迟。
并发更新的一致性：索引落盘后，对应的 key 仍可能被覆盖或删除，Compaction 搬迁数据也会改变索引指向的位置。这些更新与索引加载、落盘交错执行时，内存和磁盘中的索引可能处于不同的更新阶段。如果状态同步不当，就可能读取旧值、让已删除的数据重新出现，或访问已经失效的数据位置。
崩溃后的快速恢复：进程可能在数据写入、索引更新或索引落盘的任意阶段崩溃。重启时，需要准确识别可复用的磁盘索引和待恢复的增量更新，保证已成功写入、覆盖和删除的结果正确恢复。如果依赖全量扫描数据或加载全部索引来确认状态，恢复耗时和内存压力仍会随数据规模增长。
本题的技术难点是让磁盘索引、内存缓存和恢复机制协同工作，在有限内存下兼顾访问效率、恢复速度与数据正确性。

## 4、核心诉求
实现一个哈希 KV 引擎，支持索引持久化。在保证数据正确、持久化可靠和索引内存受控的前提下，重点提升有限内存下的读写性能，降低内存未命中时的长尾延迟和重启恢复时间。鼓励在以下方向深度探索：
索引结构与存储效率：设计内存、磁盘索引的组织方式及文件布局，探索紧凑布局、变长编码和批量读写，平衡内存占用、磁盘空间与访问效率
按需加载与自动落盘：合理设计索引加载粒度、缓存策略和落盘策略，减少不必要的磁盘 I/O，控制内存占用和长尾延迟
并发控制：协调读写、索引加载与落盘，减少锁竞争，提高并行处理能力
持久化与恢复：设计数据、磁盘索引和恢复日志的协同机制，保证崩溃恢复后的状态一致，并减少恢复开销
Compaction 调度：优化无效数据及索引的回收策略，降低后台任务对前台读写的影响
Checkpoint（可选加分项）：探索低开销的一致性副本创建方式，支持副本独立恢复，并保证原引擎后续变更不影响副本

具体约束如下：
**【引擎结构约束】**
哈希桶数量在创建引擎时确定，运行期间保持不变。可通过合理设置初始桶数量，减少桶内冲突和锁竞争
每个桶内可自由选择内存索引结构（SkipList、有序数组、std::map 等均可），并设计相应的磁盘索引结构、文件布局和访问方式
同一个 key 采用覆盖语义，读取返回最新有效值，删除后返回 NotFound。旧版本记录可保留在磁盘中，由 Compaction 回收
允许使用哈希值或指纹降低索引内存开销，但必须正确处理冲突，不得仅依据哈希值或指纹相等判定 key 相等。实现须保留完整 key 或其无损表示，并在匹配时进行精确比较。完整 key 可存放于磁盘，无需常驻内存。不得以碰撞概率低为由省略冲突处理。代码审查发现违反此要求，即使通过测试，仍判定实现不符合要求。
**【索引持久化约束】**
必须设计可持久化的磁盘索引结构，支持根据 key 定位数据，磁盘索引的组织方式和加载粒度可自由设计
磁盘索引必须支持按需加载：访问未驻留内存的索引时，能够从磁盘加载所需部分，无需预先将全部索引加载到内存
引擎启动时指定内存预算（mem_limit_bytes），须据此控制索引及其缓存的内存占用，并自动将部分内存索引落盘、释放内存
内存验收以被测进程的 VmRSS 为准，采样值不得超过 mem_limit_bytes × 110%。该限制覆盖整个被测进程，包含索引、日志缓冲、Compaction 缓冲、临时对象及自建内存池等。参赛者应为其他模块预留空间，必要时将索引实际使用阈值设为低于该预算。具体口径见第 6 节“内存限制与统计口径”
索引加载、更新和落盘过程对上层接口（Get/Put/Delete）完全透明，支持并发读写，保证同一个 key 的最新版本和删除状态正确
引擎重启后必须能够恢复并使用已持久化的磁盘索引，可结合持久化的索引元数据和 WAL 等日志恢复尚未落盘的索引更新，无需全量扫描数据文件重建索引或将全部索引加载到内存
**【持久化约束】**
Put / Delete 返回成功前，必须完成持久化同步，如 fsync / fdatasync 或等效机制，不能仅写入内存或操作系统 page cache。进程崩溃或机器宕机后，已成功的写入、覆盖和删除必须能够恢复，恢复后的读取结果须符合已成功操作的最终状态
可采用 WAL（Write-Ahead Log）或直接追加写数据文件等方式实现，选手可自行发挥，须保证数据与索引在崩溃恢复后保持一致
引擎的所有数据文件，包括数据、索引、WAL、元数据和临时文件，必须存放在 Open 指定的 data_dir 内，不得写入目录外或通过软链接存放到其他位置。Checkpoint 副本存放在 CreateCheckpoint 指定的目录内。
**【Compaction 约束】**
必须实现后台 Compaction 机制，对被删除或被覆盖的无效记录进行垃圾回收；数据位置变化时须同步维护索引，并回收磁盘索引中的无效内容
建议在文件中有效数据占比低于 50% 时触发 Compaction
**【Checkpoint 约束（可选加分项）】**
支持通过 CreateCheckpoint 接口，将引擎的一致性副本保存到指定的新目录，成功返回后可通过 KVEngine::Open 独立打开该目录
副本须对应 CreateCheckpoint 调用开始至返回之间某一时刻的完整状态，数据、索引和删除状态保持一致；允许创建期间短暂协调或阻塞写入
副本不得依赖原数据目录才能恢复，原引擎后续的写入、删除、Compaction 或原数据目录的移除均不能影响副本

客观指标总得分 S = (40% × T + 25% × R + 25% × W + 10% × O) x 80

**【正确性测试场景（必须全部通过）】**
以下列出公开测试的主要场景，具体用例和默认参数以参赛包为准。所有公开场景的索引内存预算统一为 256 MiB。提交后还将使用其他数据、参数和操作组合开展更严格的正确性测试，正式性能测试数据和评分程序不随包提供。
场景 1 基础顺序读写：顺序写入 100 万 kv，全量读取验证正确
场景 2 随机读写：随机顺序写入 500 万个 key，随机读取 500 万次，最后全量校验所有 key 的 value。
场景 3 覆盖写：对 10 万 key 各写 10 次，读取应返回最新 value
场景 4 删除：写入后删除，读取应返回 NotFound；删除不存在的 key 应返回 OK
场景 5 重启恢复：写入 100 万 kv，并执行部分覆盖写和删除，在索引加载、落盘过程中发送 SIGKILL，重启后验证所有已返回成功的操作结果正确
场景 6 混合测试：混合读、写、删除 100万 kv，验证读取结果正确。
场景 7 按需加载：生成超过索引内存上限的数据集，验证无需全量重建或加载索引即可提供服务；随机访问不同范围的 key，验证磁盘索引按需加载、读取结果正确。
场景 8 受限内存下的持续读写：写入 2000 万个不同 key，穿插覆盖、删除和旧 key 回读；线程结束后，在重新打开前后分别全量校验。
场景 9 Compaction 并发正确性：通过持续覆盖写积累无效记录，验证后台 Compaction 实际触发并回收无效数据及索引。
场景 10 Compaction 崩溃恢复：在数据搬迁、索引更新及旧文件回收期间发送 SIGKILL，重启后验证已返回成功的操作结果正确，已删除的数据不重新出现，索引不指向已回收的数据位置。
公开崩溃测试通过外部进程注入故障，不依赖引擎内部观察点，不保证 SIGKILL 恰好发生在索引落盘或 Compaction 的某个内部步骤。

**【Checkpoint 加分测试（加分项）】**
以下为官方 Checkpoint 验收要求，公开参赛包提供其中部分场景供自测
一致性与独立恢复：写入 100 万 kv，执行部分覆盖写和删除后创建 Checkpoint；通过 KVEngine::Open 打开副本目录，全量验证数据及删除状态与创建时一致
副本隔离：创建 Checkpoint 后，继续对原引擎执行写入、删除和 Compaction；关闭原引擎并移除原数据目录，再打开副本，验证副本内容不变且可正常读写
并发创建：在持续读写期间创建 Checkpoint，验证副本对应创建期间某一时刻的一致状态，原引擎运行正常
失败处理：在 Checkpoint 创建过程中终止进程，原引擎必须能够正确恢复。若副本尚未完成持久化提交，Open 必须返回错误，不得作为空库或部分数据正常打开；若副本已经完整提交但接口尚未返回，则允许恢复为有效的一致性副本。

**【Compaction 加分测试（加分项）】**
评测采用对同一批 key 多轮覆盖写入的负载，产生可回收的旧版本数。value 大小显著大于 key，以降低索引及元数据开销对空间回收效果判定的影响。停止写入并给予统一的后台回收时间后，存活 KV 的逻辑字节数占引擎数据目录文件总字节数的比例达到 70% 及以上，且通过数据正确性与重启恢复验证，可获得 Compaction 加分。

**【评测环境与缓存控制】**
各测试场景独立运行，使用独立的数据目录
每个性能测试场景及每轮测试开始前，由评测方统一清理操作系统 Page Cache，正式压测期间不主动清理 Page Cache

**【内存限制与统计口径】**
mem_limit_bytes 为引擎内存预算。评测方使用外部 Python 采样 /proc/<pid>/status 中的 VmRSS，进程 RSS 上限为 mem_limit_bytes x 110% + 测试程序预留额度，超过即终止进程并判定内存超限。
RSS 包含实际驻留的堆内存、分配器空闲页及碎片、线程栈、文件映射、共享内存、程序和共享库页面。普通文件读写产生、未映射到进程地址空间的 page cache 不计入。外部 Python 的内存不计入，被测进程内的 C++ 测试框架和缓冲计入。
公开统一测试入口默认每 2 ms 采样一次，覆盖初始化、恢复、运行和销毁。采样并非内核硬限制，可能遗漏短暂峰值。无法获取有效样本、内存超限、超时或意外退出均判失败。

**【评测方式】**
公开测试统一通过 Python 脚本运行，CMake 仅负责构建。Python 负责启动各场景、监控 RSS、控制超时、注入故障并汇总结果。直接执行 C++ 测试程序仅用于调试，不构成完整验收。
吞吐量和读写延迟围绕接口调用统计。崩溃恢复测试由外部控制程序向评测进程发送 SIGKILL，再启动新的进程验证恢复结果。公开测试模拟进程崩溃，不模拟机器断电；通过该测试不能替代持久化同步要求及代码审查。

### 7.3 评测规则
公开测试：提交前须按默认验收规模通过全部必选公开测试。Checkpoint 未实现时可跳过，已实现则须通过对应测试。公开测试不计性能分。

提升业务稳定性：降低因索引内存超限导致的进程 OOM crash 风险，通过索引按需加载和快速恢复，减少访问长尾抖动与重启耗时，提升核心推荐/广告链路的 SLA
