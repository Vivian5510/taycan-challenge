# 恢复后的 caller 主干与 Helio 实验分支对照

本报告只使用 2026-11-04 本轮新测数据。caller 来自恢复后的 main `cdbc644`，Helio 来自 `experiment/helio-integration-audit` 的 `90eedee`。旧的 Boost.Fiber/event `main-event` 没有参与本轮，也不再称为当前主干。

## 构建与身份

caller 新建 Release 构建；Helio 使用上轮审计后冻结的 Release 二进制，SHA256 与其提交内原始结果一致，未重配、未重新编译或修改。双方编译器为 AppleClang 17.0.0，Release 公共优化配置为 -O3 -DNDEBUG，共享负载源码 SHA256 一致；各自必须的运行时依赖和编译定义不同，实际编译命令保留。caller使用-std=c++17，Helio原工程使用-std=gnu++17，优化配置相同，不声称全部编译参数逐字一致。不是此前 caller RelWithDebInfo 与 Helio Release 的对照。

共同构建条件：data-log、fsync、POSIX 后端选择、512B 提交块、1MiB 日志页、4KiB overflow 页、GC 和额外 pipeline 关闭。完整共同参数、源码/生成源码、二进制、动态库和 Boost 静态库哈希见 results.json，运行前后核对。POSIX 后端选择相同不代表实际执行方式相同：caller 使用 POSIX AIO，Helio 的已启用 hook 使用原版单 worker 文件线程池，这是待比较实现的一部分。

## 测试条件与范围

macOS ARM64 原生，同步 KVEngine API，32 个外部调用线程，总预算 4GiB，Key 32B / Value 256B，相同 seed=20261021、uniform。双方成功返回前完成持久化同步；没有关闭 fsync、提前 ACK 或更改负载断言。

caller 使用原有自适应 group collect（上限50µs）；Helio 显式比较10µs、50µs窗口，保留两者，没有按结果挑一个窗口替代另一负载的配置。它们的收集算法不同，窗口数值相同也不等于相同批次。

热负载4096 Key，预热2秒、测量8秒、逐操作延迟，每模式各3轮，正序/反序/轮转交错。混合为60%读/30%写/10%删除；纯更新均为Put。33个性能单元串行运行。每模式另完整装载1,000,000唯一Key；disk-region-read先完整装载2,000,000唯一Key，再预热2秒、随机读8秒，均校验Value内容，后两项各1轮。

2M记录超过 F2 日志内存缓冲，但没有清空OS页缓存；disk-region-read不是物理盘冷读。4096 Key是调度与提交诊断，不是正式2亿Key/4GiB索引落盘验收。

## 正确性门槛

本轮状态 `PASS`。验证条目状态：{'PASS': 12}；性能状态：{'PASS': 33}。

三个模式分别运行原SDK basic/concurrent/recovery（2000 Key、4GiB、31读+1写的版本边界用例），并各执行原SDK SIGKILL协议5次，共15次；所有验证完成后才启动性能矩阵。这些是开发规模验证，不把12条wrapper记录表述为12个独立故障，亦不宣称通过完整默认规模。

## 差异解释

混合读写：caller中位327,161 ops/s；Helio10为175,702（相对caller中位数-46.3%）；Helio50为168,056（-48.6%）。

纯更新：caller中位141,858 ops/s；Helio10为85,099（相对caller中位数-40.0%）；Helio50为142,693（+0.6%）。

热读：caller中位682,577 ops/s；Helio10为463,334（相对caller中位数-32.1%）；Helio50为465,078（-31.9%）。

caller的Get由多个SDK调用线程直接执行；Helio把数据访问集中到一个owner。因此热读包含执行并行度差异，不能把差距全部解释为fiber切换成本。写入则涉及caller-led与owner提交、外部完成通知、文件交接、合批和读写协调的组合。本轮比较完整实现，不量化每项因果占比。

写/组和CPU覆盖装载/预热/测量/关闭，吞吐和p99仅覆盖测量，不能直接换算精确阶段占比。磁盘增长是逻辑文件字节，不是设备写入量或NAND写放大；相同持续时间不同吞吐产生的总增长不能直接视为效率差异。

整轮CPU µs/操作以进程所有子线程user+system CPU时间，除以日志中prepare、warmup、measure各阶段最终操作数之和，包含初始化/维护/关闭成本；不是测量期单独采集的CPU成本，也不是owner单核时间。本轮Helio吞吐较低但整轮单位操作CPU消耗也较低，因此不应将吞吐差异解释为所有性能维度均退步。

## 状态与限制

不修改引擎，不合并实验分支，不将旧main-event成绩替代caller。共享交互主机的三轮短测不足以证明统计显著或跨机器普适结论；没有使用虚拟机，也不是正式Linux/NVMe、GC/compaction组合或2亿Key/4GiB成绩。

运行中最低可用空间155.5GiB，观察到单库峰值763.4MiB；守护20GiB余量和2GiB单库限制，成功数据库删除，日志、RSS、结果与哈希保留。任何FAIL/未执行状态保留，不自动重跑。
