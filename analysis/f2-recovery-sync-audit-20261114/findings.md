# 已核实的性能差距

固定数据：百万唯一Key、32/256B、4GiB、同seed、共享驱动，只测完整装载。
每次调用同步返回后才计入完成数。全矩阵逐格运行，无其他测试或编译重叠。

1. RocksDB高吞吐确实使用了同步：暂停实际内核fsync时没有ACK；注入EIO返回失败；
   成功后强杀、重开和相同部分页丢失模型均保留已确认的写/删。不是sync标志开启但未执行。
2. 32线程默认RocksDB百万调用合成62,425次WAL同步，约16.02调用/次，吞吐210,396。
   F2百万调用对应1,000,001次hot-log同步，吞吐11,827。
3. RocksDB用官方max_write_batch_group_size_bytes=1限制后继请求加入组，百万调用变成
   百万次WAL同步，吞吐34,163。该控制不禁用WAL或降低同步条件，实测计数确认合批消失。
   默认与此控制约6.16倍；此控制与F2仍有约2.89倍差异。这个乘法分解只描述本轮，
   不等同于普遍的算法倍数。
4. 单线程两边都每次同步：F2 11,978，RocksDB39,494。F2调用数1到32没有增长，
   与实例写互斥覆盖刷出、fsync和索引发布整段代码一致。
5. 独立生成源码计时（不改正常内核默认开销）测得每次F2写约78.1us：
   flush44.98us（发起/等待HybridLog写完成），sync30.23us（选择同步依赖、fsync及句柄处理），
   session0.86us、apply0.52us、gate0.40us、发布0.45us、seal0.13us。
   内核fsync本身累计23.88秒，约23.88us/写。flush+sync约占96%，
   foreground checkpoint计时0.42秒；后台GC工作可能体现在flush/gate等待，不能把其成本都算成0.42秒。
6. 现有inline后端单线程同条件控制14,718（原AIO11,978），提高约23%。这说明AIO提交/
   轮询有成本，但换成inline也远未追平RocksDB。额外inline32线程格与诊断编译重叠，
   原结果保留但不纳入归因。没有据此切换产品默认IO后端。
7. 去掉插桩的独立32线程格：F2 12,734、RocksDB141,338。插桩会改变调度和合批比例，
   RocksDB21万不是稳定硬件上限；无插桩仍有约11.1倍差距。所有数据是单轮诊断，无置信区间。

文件缓存策略也不同：F2文件F_NOCACHE、RocksDB WAL buffered。两边等待相同内核fsync，
这保证同步级别相同；它不把每次刷写的路径成本变得相同。不能把剩余约3倍全部归因到AIO，
也不能归因到F2索引算法。优先方向应是降低单次数据日志flush开销，并在实验分支评估
有界提交流水线/合批；main按用户要求不恢复group commit。

本轮是macOS fsync/OS page cache丢失口径；没有拿fsync实测代替物理设备断电证明。
若测试物理掉电，双方需要同一更强设备flush策略并重新测量，不能只给其中一方升级F_FULLFSYNC。
